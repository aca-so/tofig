Four steps
from artifact to canvas.

Two of them happen in the conversation, two of them happen in Figma. The first two are the ones that decide whether the last two work.

  1. Get the source, not a picture

    Claude renders designs as Artifacts, and an Artifact is a real HTML document. There are two ways to get at it.

    • Copy or download the artifact's source. The artifact panel can hand you the file it is rendering. You want the raw HTML, not an image and not a PDF.
    • Or ask for it in the conversation. Slower by one message, better by a mile, because you get to specify the shape of the file while you are asking for it. That prompt is the next step.

    Save it with a .html extension. tofig takes a pasted string or a dropped file, so either is fine.

  2. Ask for a file that converts

    This is the step that decides everything downstream. A Claude artifact is built to run in a browser tab with the whole internet available to it. tofig runs inside a Figma plugin that has none of that. Say so up front and Claude will write the file the plugin can actually read.

    export prompt 
    Give me this design as a single self-contained HTML file.

- All CSS inline, in one <style> tag. No external stylesheets, no CDN links.
- No JavaScript. The finished layout must exist in the HTML itself, not be
  built at runtime.
- Images as data: URIs, or drawn as inline SVG. No remote image URLs.
- Use a font family that exists in Figma, or a plain system stack, and tell
  me which one you used.
- Set an explicit pixel width on the outermost element so the artboard has a
  fixed size.
- No iframes, no <link> tags, no icon fonts.

    Paste it into the conversation after the design is already on screen. It works as a follow-up message, so you are not regenerating the design, only re-emitting it.

    Every line in that prompt is there for a reason.

    inline <style> only
    The plugin declares networkAccess: none. A <link> to a stylesheet resolves to nothing, so the document renders unstyled and you convert a column of black text on white.
    no CDN scripts
    Same block, one layer deeper: the plugin UI runs from a data: URL, which is an opaque origin. A script tag pointing at unpkg or a Tailwind CDN build never resolves.
    no runtime rendering
    tofig renders your document and reads the computed geometry back out. If the markup is an empty root element that a framework fills in later, there is nothing on screen to measure.
    fonts Figma has
    A face that is not loaded in your document is substituted for the nearest match, then Inter. tofig reports every substitution it makes, but a face you did not choose is still a face you did not choose.
    data: images, inline SVG
    Remote images are never fetched, so <img src="https://…"> arrives as an empty frame. Inline SVG comes through as vector paths you can reshape.
    an explicit width
    The artboard is measured, not guessed. A fixed outer width is the difference between a 1440 frame you asked for and whatever the renderer's default viewport happened to be.

  3. handoff the file leaves the conversation and lands on a canvas

  4. Run tofig and convert

    Open a Figma Design file or a Figma Slides file, run tofig from the plugins menu, then paste the markup into the window or drop the .html file onto it. Press Convert.

    There is no mode to pick. tofig reads figma.editorType and targets the right output on its own: frames on the canvas in a Design file, real slides in a Slides file. A multi-section page arrives as one frame per section, each clipped to its own bounds.

    Nothing leaves your machine. The render happens in a hidden iframe inside the plugin window, on your computer, with the network switched off.

  5. What lands on the canvas

    Real Figma nodes, with real properties. Text you can retype and rewrap, mapped to the nearest available weight. Inline SVG as editable vector paths with their control points intact. Fills, linear gradients, strokes, corner radii and opacity arrive as native paints and properties rather than baked into the pixels.

    FrameTextVectorImage fill GradientStrokeRadiusOpacity

    Layout is absolutely positioned. That is a deliberate trade for visual fidelity: you get placement that matches the render to the pixel, not auto-layout constraints. Auto-layout is on the roadmap, and until it lands this is the honest description of what you get.

Some artifacts are
live apps, not documents.

This is the common case for Claude specifically, so it is worth knowing before it happens rather than after. Claude often ships an artifact as a component that assembles itself when the page loads. Wonderful in a browser tab. Impossible inside the plugin.

A framework runtime

The document is an empty root element plus a script that builds the interface. There is nothing to measure until the script runs, and it cannot run.

CDN imports

A <script src> pointing at unpkg or esm.sh, a Tailwind CDN build, a Google Fonts stylesheet. Every one of those is a network request that the plugin will not make.

localStorage and friends

Browser storage on an opaque data: origin throws immediately. The artifact fails before it paints its first pixel.

This is a sandbox limit, not a bug.

No network and a data: URL origin are exactly what make the plugin safe to point at markup you did not write. The workaround keeps that property.

The quick fix is upstream. Go back to the conversation and ask for the same design as static HTML and CSS with no framework, using the prompt above. It is one message, and it removes the problem at the source rather than working around it.

The fix for a file you already have is to render it in a real, unrestricted Chrome on your own machine and import the result. Same extractor, same output, just a browser without the sandbox. The command writes a .tofig.json next to the input; drop that into the plugin and it imports directly.

Requires Node and a local Google Chrome or Chromium. Still entirely local: nothing is uploaded, by tofig or by acaso.

~/exports 
$ npx --package=@aca-so/tofig tofig-render claude-export.html
  › launching local Chrome
  › rendering claude-export.html
  › extracting 312 nodes
  ✓ wrote claude-export.tofig.json · 104 KB

--package= is needed because the binary is named differently from the package. In the plugin, drop the .tofig.json exactly the way you would drop an .html file.

Ship the design,
not a picture of it.

The plugin is published to the acaso organization in Figma. The renderer is a separate, optional CLI, and you only need it for the artifacts that will not sit still.
